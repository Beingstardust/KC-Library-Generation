# 70. INT-21: the defining-equation rescue reads through LaTeX formatting commands

Commit `69e797a`. Full measurement record is in the commit message; this is the reading path and
the part the commit does not record.

## Where it sits

Three interventions in a row all serve one gate. `is_defining_equation` decides whether a row
states the equation that DEFINES a unit, which is what lets the rescue admit that row below the
cross-encoder floor. Each intervention removes one reason the pattern could not see an equation
that was plainly there:

```
INT-20  the name is letter-spaced       "R a n d I n d e x = ..."
INT-21  the name is wrapped             "\mathrm { R a n d I n d e x } = ..."
INT-22  the sentence is spliced         a DIFFERENT sentence's math sits inside this one
```

INT-20 and INT-21 are the same defect seen twice, because the PDF extractor emits both together:
a display equation's function name is nearly always both wrapped and letter-spaced. INT-20 alone
therefore fixed almost nothing on its own for multi-word names, since collapsing "R a n d I n d e x"
produces "RandIndex" and destroys the word boundary the pattern requires. INT-21 supplies the
tolerant match that makes INT-20 pay off. They should be read as one change in two commits.

## Why widening this pattern is safe, and why the argument does not generalise

Every other admission rule in this pipeline is a filter that could let foreign content in if
loosened. This one cannot, and the reason is worth stating precisely because it is the only place
in the audit where a deliberate loosening was accepted:

> the reduced text still has to match THIS unit's own name

A wrong reduction can only fail to match. It cannot cause unit X's packet to admit unit Y's
formula, because the pattern is built from X's name and Y's formula does not contain it. That is
why `normalise_equation_text` and `collapse_letter_spacing` are called from exactly one place, and
why INT21-7 is a guard that pins the call site rather than a guard on behaviour. If either function
is ever reused elsewhere, this argument silently stops applying.

`"Rand\s*Index"` still cannot match "Random Index" - after "Rand" that text reads "om" - which is
what INT21-5 asserts.

## What sabotage found, and the lesson that generalises

Three of seven guards were wrong when written, and INT-21's own sabotage found all three. Two of
them share one root cause worth naming, because it recurred across this whole audit:

**A guard whose fixture does not need the mechanism it tests will pass without it.** INT21-1's
fixture was satisfied by brace-stripping alone, so deleting the wrapper substitution changed
nothing observable. INT21-5's fixture needed no reduction at all, so an early exit answered it
before the tolerant pattern ran, and widening that pattern to a wildcard SURVIVED sabotage.

The fix in both cases was the same: make the fixture a case that ONLY the named mechanism can
satisfy. For INT21-1 that meant hunting the corpus for a row the wrapper substitution actually
buys - there is exactly one, Separation's graph-based defining equation, which the substitution
rescues by shortening a parenthesised argument list below the pattern's own 30-character limit.

**The early exit was itself hiding a real defect.** Chasing INT21-5 showed that `is_defining_equation`
returned early when the reduction changed nothing, so "RandIndex = 4" - Rand Index's own defining
equation, already collapsed in the source - was rejected. The strict pattern requires a space
inside the name and the tolerant one never ran. Removing the exit fixed a real corpus case that no
one had reported. Sabotage on a guard found a bug in the code, not just in the guard.

## Result

Seven units changed, +18 rows, zero support-state moves, zero units losing formula rows without
gain. Rand Index, Accuracy, Separation and Cohesion all gain their defining equations, and all four
reach the final drafts. See doc 72 for how the drafts state them.
